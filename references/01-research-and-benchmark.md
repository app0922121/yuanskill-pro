# 01 · 需求解构 · 形态判定 · 定义"好" · 竞品调研 · 开源挖掘 · 逐段对比

研究阶段（阶段 0 – 4）。阶段 2 的 YouTube 部分另见 `05-youtube-research.md`。目标：动手写之前，先把"要解决什么、该做成什么形态、世界最优解长什么样、最成熟的实现怎么做"搞清楚。

---

## 1 · 需求解构（阶段 0）

### 1.1 四问框架

收到需求，先在 `<thinking>` 里答完，别急着写：

| 维度 | 问题 | 常被漏掉的点 |
|---|---|---|
| 表层需求 | 用户明说要什么？ | 照字面做 ≠ 满足意图 |
| 深层意图 | 真正想解决的问题？ | "优化这个 prompt" 背后往往是"输出不稳/不像人/不准" |
| 隐含约束 | 受众、平台、语气、合规、成本、上下游？ | 面向美国用户？闭源商用？token 预算？ |
| 成功标准 | 什么样的输出算"好"？可验证吗？ | 见 §3 |

**澄清提问（DETAIL 模式）**：只问 2–3 个能改变方案的关键问题，别问能自己查/自己定的。给出推荐默认值让用户否决。

### 1.2 需求卡 6 问（产物是 skill 时追加）

四问定方向，6 问出骨架。花 5 分钟填完，答案基本就是 SKILL.md 的骨架：

1. **问题**：要自动化的到底是哪件事？
2. **场景**：用户会怎么开口？（原话，不是术语）
3. **输入**：什么格式、从哪来、可能有哪些异常形态？
4. **输出**：交付物是什么、存到哪、叫什么名字？
5. **规则**：必须遵守的硬要求（格式/数值/术语）？
6. **禁止清单**：明确不能做什么？

> 需求不需要完美。先写初版、在使用中迭代——很多需求是用完才浮现的，不是规划出来的。

## 2 · 形态判定（阶段 0.5）

**这是最容易被跳过、代价却最大的一步。**做成 skill 是有成本的：创建要时间、维护要精力、每次触发消耗一次工具调用并把正文常驻上下文。

### 2.1 五种形态，选一种

| 形态 | 什么时候选 |
|---|---|
| **直接提示词** | 一次性、简单、高度灵活的任务 |
| **全局配置**（CLAUDE.md 等） | 始终生效的规则（"回复要简洁""缩进用 4 空格"）——贴在墙上，别写进每份菜谱 |
| **工具 / 命令行** | 一行命令能干（图片转格式、压视频）；不需要你的经验就能完成 |
| **脚本** | 同样输入必须产生同样输出、要求 100% 确定性（格式标准化、数值精度、日期归一） |
| **skill** | **反复做 × 要一致性 × 流程已稳定**，且既有死规则又需灵活判断 |

### 2.2 该不该做成 skill：三问

1. **这件事你会反复做吗？** 只做一次 → 提示词就够。
2. **对结果一致性有要求吗？** 头脑风暴/创意写作反而希望每次不同 → 不需要 skill。
3. **流程是否已经基本稳定？** 自己还在摸索 → **别急着固化，过早固化会把错误的流程锁死**，之后每次调用都重复同一个错误。

三条满足得越多越值得做；一条都不满足就别折腾。

### 2.3 决定做了，也要知道四个限制

| 限制 | 应对 |
|---|---|
| 结果不完全确定（同输入未必同输出） | 需要确定性的环节拆出来交给脚本 |
| 通用与可靠难两全（规则越严适用越窄） | 该严的严、该松的松；有对照表的写死，因情况而异的只给方向 |
| 触发不一定准 | description 反复测（见 `references/02-technique-library.md` §4） |
| 不同模型表现不同 | 复杂产物分别测；强模型少给细节、弱模型多给步骤 |

### 2.4 最稳的起步方式

先让模型**裸跑一遍真实任务**，观察哪里不对，再针对短板写产物，边用边改。这既是起步方式，也天然给你留下了阶段 7 需要的**基线**。

## 3 · 定义"好"（阶段 1）

**无可验证标准 = 无法优化，先补齐。**

### 3.1 从锚点到检查项

先把目标翻成**可检验锚点**：

- 传播类 → "脱离上下文也成立、有反差、想截图"
- 事实类 → "每句可追溯到某输入字段/信号"
- 工程类 → "schema 校验通过率、解析不崩、同输入稳定"

再把锚点落成**能直接判对错的检查项**：

| | 例子 |
|---|---|
| ✔ 好的检查项 | "纪要包含待办事项清单"；"每个待办标注了负责人"；"篇幅不超过原文 30%"；**"产物被正确触发"**（触发本身就是一个要验的检查项） |
| ✘ 太模糊 | "输出质量好"——没法判断 |
| ✘ 太脆弱 | "必须出现'总收入：X$'这个精确措辞"——换个说法就算失败 |

### 3.2 两条纪律

- **检查项可以后补**：第一次跑之前你未必知道该查什么。先写用例，看到一个"不够好"的结果之后，"好"长什么样才说得清。
- **检查项本身也要迭代**：跑几轮后，不管有没有产物都能过的（无区分度）删掉换一个；改了好几版都过不了的，要判断是检查项不合理还是产物需要大改。**标准是活的。**

## 4 · 领域判定与信源分层调研（阶段 2，BASIC 也必做）

**依据**：用户 2026-11-06 要求：任何问题都先判领域，再找这个领域的网站、门户和产品，并把 YouTube 纳入默认调研。方法来源：
- STORM 先找相邻主题的现成目录；
- Jina 判「最权威的语言/地区」，并按域名出现频率加权；
- open_deep_research 规定产品类问题直达一手；
- Anthropic 的多智能体研究系统反内容农场；
- 本机 strategy-essence 的覆盖表、停止规则和升级链。

以上「已读原文」的部分，见 CHANGELOG v2.1.0。

问题设成：「**这件事属于哪个领域？这个领域里谁说了算、谁做得最好、靠什么机制成功？**」

### 4.1 判领域（先写进调研文件）
写 5 项：
- 领域名；
- 上级领域；
- 相邻领域 2–3 个；
- **这个领域最权威的语言或地区**：不看用户用什么语言提问。例如 AI 和开发工具以英文为主，中国本土市场以中文为主；两种语言都重要时，分开建表；
- 问题类型：产品 / 方法 / 学术 / 政策 / 技术实现。

拿不准时，并列写出候选领域，不要强行只选一个。

### 4.2 先写一句自己的判断
看任何标杆之前，先用一句话写下当前最佳答案，标「假设」。这样做是为了避免被别人的结论带着走。调研结束后，回头对照它被推翻了还是被坐实了。

### 4.3 建五层信源表

| 层 | 是什么 | 例子（每次重新找，不照抄） |
|---|---|---|
| L1 一手与官方 | 官方文档、标准、监管、原论文、财报 | 厂商 docs、RFC、arXiv |
| L2 门户与聚合 | 行业门户、垂直媒体、榜单、目录、awesome-list | G2、Product Hunt、36氪、awesome-xxx |
| L3 相关产品 | 头部、腰部、新锐各 2–3 个：官网、定价页、changelog、实际试用 | — |
| L4 社区 | 真实用户和从业者的讨论 | Reddit、HN、GitHub Issues、知乎、V2EX、小红书 |
| L5 视频 | **YouTube 必查**，按 `references/05-youtube-research.md` 做 | — |

学术类题目，L1 加查论文库：Semantic Scholar、arXiv，中文加知网。

**怎么填**：
1. 先做 3–5 次短而宽的搜索，数一下哪些域名反复出现，把它们作为 L2 门户候选补进表里。
2. 反复出现不等于权威：靠 SEO 排上来的内容农场一律降级。
3. 每个站点要实际搜到、打开过，才能写进表；搜不到就写「未找到」，不凭记忆编。

### 4.4 检索矩阵
- **双语**：领域最权威的语言搜一轮，另一种语言（中文或英文）再搜一轮。
- **两个时段**：近 12 个月一轮；3 年前一轮，用来看做法怎么演变。
- 搜索工具不一定支持 `site:`，先试一次；不支持就把站点名写进查询词。

### 4.5 停止规则（每个要回答的问题）
- 找到 3 个以上相关来源，且关键结论有 2 个以上**独立**来源（10 篇转载同一份通稿只算 1 个），就停。
- 最近 2 次搜索没有新信息，停。
- 搜了 5 次还没有结果，标「缺口」，写明试过哪些办法。

### 4.6 拿不到时逐级换办法
依次尝试：
1. 换抓取方式（curl，或用浏览器以只读方式打开）；
2. 查网页存档（web.archive.org）；
3. 找同一事实的另一个一手出处；
4. 换一个代理指标；
5. 把需要的东西写成给用户的具体请求。

**工具先测再用**：平台和工具都会变（Alexa 已经停服；WebFetch 读不了 YouTube）。
**红线**：不伪装浏览器身份，不关证书校验，不代填人机验证，浏览器只读。

### 4.7 覆盖表（交付前必须填满）
每一格都要填一种状态：**已查（N 条）/ 查无 / 不可达（原因）/ 需用户（具体请求）**。空着就不合格。模板见 `assets/eval-kit.md` §5。

```
| 层 | 查了哪些站/产品/视频 | 状态 | 关键机制 → 出处 |
| L1 一手 | … | 已查 4 | … |
| L5 YouTube | 候选 10 · 读正文 3 · 据简介 2 | 已查 5 | … |
```

### 4.8 提炼机制，不堆链接
- 每条结论都要能写成「某某靠**什么机制**成功」，并注明出处和层级。
- 只有 L4、L5 支撑的结论，标「待一手核实」。
- 做跨文化校验：某个机制是否依赖特定语境。例如中文「盲派断语」这类锚点，不能直接迁移给英文用户。
- 最后输出 3–6 条「可抄的成功机制 + 出处」，再回到 4.2，看自己的初始判断被推翻了还是被坐实了。

**省成本**：L1–L5 的调研交给子代理按层分头做，结果写进文件。主会话只读压缩后的结论，不读网页原文和字幕全文。

## 5 · 开源最成熟实现挖掘（阶段 3）

竞品给"要什么感觉"，开源实现给"工程上怎么做稳"。

- **找最成熟的同类实现**：GitHub 按 star / 活跃度 / 生产级找同赛道仓库；定位核心 prompt/逻辑文件（如 qimen 的 `buildInterpretationPrompt()`）。
- **拉到本地读正文，别只看 README**：真正的工程经验在代码/prompt 正文里。
- **抽"字段级工程"经验**（成熟实现最值钱的地方）：
  - 每个输出字段的**字数上限 / 格式模板 / 触发条件 / 禁用词黑名单 / 正例**；
  - 输入→输出的**强/弱耦合**方式；
  - 失败定义与兜底。
- **实物核对优先于书面转述**：书、文档、博客说的，和作者自己代码里做的，经常不一致。**能拿到实物就核对实物**——不一致本身就是高价值发现（说明那条是纸面建议，不是被验证过的必需项，应下调优先级）。
- **查 LICENSE**：借代码/架构进闭源商用前先确认许可（AGPL 有传染性）。
- 输出：一份"可抄点清单 + 该实现的短板 + 哪些经实物核对"。

## 6 · 逐段对比与取舍（阶段 4）

把「你的现状」与「标杆」按多维度**并排**，逐维判谁更强、为什么。参考维度（按任务增删）：

| 维度 | 看什么 |
|---|---|
| 角色/定位 | 职能定义 vs 人格定义 |
| 硬约束框架 | 是否有"违反即无效"的铁律分层 |
| 数据→产出映射 | 强耦合（可审计）vs 松耦合（有重点） |
| 基调/风格控制 | 是否分档定基调 |
| 反空洞机制 | 字段级黑名单 / 差好示例 |
| 字段规格化 | 每字段是否有字数/格式/触发/示例 |
| 差异化/温度 | 人设、第二人称、关系语境 |
| 传播/增长设计 | 是否为分享/转化而设计 |
| 生成过程 | reasoning-first、confidence、自检 |
| 稳定性/兜底 | schema 校验、重试、静态兜底 |
| **触发工程** | description 是否覆盖高频说法（skill 形态） |
| **上下文预算** | 是否分层加载、正文是否克制（skill 形态） |
| **实测闭环** | 有没有题库、检查项、基线对比 |

**取舍铁律**：

- **互补 > 替代**：多数情况两者各强一半。**保留自己的差异化优势，只抄能补自己短板的。**
- 抄**机制**不抄**内容**（抄"字段级黑名单"这个做法，不抄它具体那几个词）。
- 每个"抄/留"决策写明理由，形成对比取舍表（可做成 HTML 可视化对照，便于复盘）。
- **标杆不是全都对**：明确列出"不建议抄的"，尤其是那些抄了会让自己退化的维度。
